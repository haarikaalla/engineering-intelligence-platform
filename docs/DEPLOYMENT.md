# Deployment Guide

## Container images

```bash
docker build -t registry.example.com/eip/backend:1.0.0  backend
docker build -t registry.example.com/eip/frontend:1.0.0 frontend
docker push registry.example.com/eip/backend:1.0.0
docker push registry.example.com/eip/frontend:1.0.0
```

Both images run as non-root users. The backend image includes `git` for cloning.

## Docker Compose (single host)

`docker compose up -d --build` starts PostgreSQL, Neo4j, ChromaDB, backend and frontend with named volumes.
Put a TLS-terminating reverse proxy (nginx, Traefik, Caddy) in front of port 3000 for anything beyond a laptop.

## Kubernetes

Manifests live in [`deploy/k8s`](../deploy/k8s) (Kustomize).

```bash
kubectl apply -f deploy/k8s/namespace.yaml
kubectl -n eip create secret generic eip-secrets \
  --from-literal=POSTGRES_PASSWORD='...' \
  --from-literal=DATABASE_URL='postgresql+psycopg://eip:...@postgres:5432/eip' \
  --from-literal=NEO4J_PASSWORD='...' --from-literal=NEO4J_AUTH='neo4j/...' \
  --from-literal=API_KEY='...' \
  --from-literal=OPENAI_API_KEY='...'          # and/or ANTHROPIC_API_KEY, GITHUB_TOKEN
# edit image names in kustomization.yaml and the host in ingress.yaml / config.yaml (CORS_ORIGINS)
kubectl apply -k deploy/k8s
```

What is deployed:

| Component | Kind | Notes |
|---|---|---|
| frontend | Deployment + HPA (2–6) | the only workload exposed through the Ingress |
| backend | Deployment (1 replica, `Recreate`) | workspace PVC; readiness/liveness on `/api/health`; read-only root FS |
| postgres / neo4j / chroma | StatefulSets with PVCs | reachable only from the backend (NetworkPolicy) |

In production prefer managed services (Azure Database for PostgreSQL / RDS, Neo4j Aura) and point the
`DATABASE_URL` / `NEO4J_URI` settings at them; drop the corresponding StatefulSets from `kustomization.yaml`.

### Scaling for very large repositories

* **Backend replicas**: analysis artifacts live on the workspace volume. To run >1 replica use a
  `ReadWriteMany` storage class (Azure Files, EFS, Filestore) and switch the Deployment strategy to `RollingUpdate`.
* **Throughput**: `PIPELINE_WORKERS` controls concurrent analyses per pod. The pipeline is a pure function of a
  repository id (`app.ingestion.pipeline.run_pipeline`), so it can be moved to a Celery/Arq/K8s Job worker without code changes.
* **Limits**: `MAX_FILES`, `MAX_FILE_SIZE_KB`, `CLONE_DEPTH` bound memory and time; vendored/generated folders are skipped.
* **Memory**: budget roughly 1 GB per 1M LOC under analysis; raise backend limits for monorepos.
* **Embeddings cost**: with OpenAI embeddings each chunk is embedded once per analysis; set
  `EMBEDDING_PROVIDER=local` to keep code on-premises.

### Air-gapped / regulated environments

* `LLM_PROVIDER=none`, `EMBEDDING_PROVIDER=local`, `ENABLE_OSV=false` — no outbound calls except `git clone`.
* Point `ALLOWED_GIT_HOSTS` at your internal Git server.
* The built-in advisory list still flags well-known critical CVEs (Log4Shell, Spring4Shell, …).

### Observability & operations

* Health: `GET /api/health` (capabilities, LLM, graph and vector-store status).
* Logs: structured to stdout; pipeline timing is recorded in each repository overview (`pipeline.duration_s`).
* Backups: PostgreSQL (metadata, results, chat), Neo4j volume, and the workspace PVC (artifacts + RAG index).
  Everything can also be regenerated by re-analyzing repositories.
